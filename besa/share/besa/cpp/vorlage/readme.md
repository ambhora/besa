# vorlage

A C++ project generated by BESA. The project vendors its BESA CMake module under `cmake/besa`, so it
can configure and build independently of the Python `besa` command after generation.

## Development environment

The project includes a Spack environment for development tooling. The local `dev-env` bundle
provides the tools needed to build, test, and document the current checkout. The central
`ambhora/amstack` repository is declared so shared Ambhora development dependencies, such as
`properdocs`, can be resolved without any user-level Spack repository setup.

```bash
spack env activate .
spack concretize
spack install
```

No `spack repo add` setup is required. Both the remote amstack repository and the local development
repository are declared directly in `spack.yaml`.

The local `dev-env` recipe is also the development description consumed by `amstack sync`
when constructing the installable `vorlage` package. The development environment does not install
`vorlage` itself; package installation through amstack is a separate operation. Development-bundle variants only control which tools are present in the environment.

## User documentation

Enable the `user-docs` feature when configuring the project:

```bash
cmake -S . -B build -DPROJECT_FEATURES=user-docs
```

The two documentation tools have deliberately separate responsibilities:

- `docs/` and `properdocs.yml` define the non-versioned project website.
- `api-docs/index.md` and `cpdoc.yml` configure the standalone, versioned API reference.
- the installed `properdocs-cpdoc` plugin mounts cpdoc below `reference/api/` and resolves
  `@apidocs::...` links from project Markdown.

Build the complete publication site with:

```bash
cmake --build build --target user.docs
```

The deployable artifact contains the ProperDocs site plus cpdoc's versioned subtree:

```text
build/doc/site/
├── index.html
├── reference/
│   ├── index.html
│   └── api/
│       ├── versions.json
│       ├── main/
│       └── <tag-or-branch>/
└── .nojekyll
```

Every cpdoc page links back to the non-versioned project site and carries its own API-version
selector. Cross-site links are semantic: API Markdown/comments use `projectdocs:` (or the supported
`@projectdocs{...}` source-comment spelling), while ProperDocs Markdown uses
`@apidocs::qualified::symbol` or `@apidocs[v0.2.0]::qualified::symbol`.

`cpdoc.yml` owns API version selection. Supported selectors include `all`, `latest:N`,
`range:<comparators>`, and `refs:<ref,...>`. `CPDOC_VERSIONS` overrides the configured selection for
one invocation. API variants are declared by `besa.toml`; an API-only CMake build can constrain them
locally with `BESA_API_VARIANTS` without changing the project model.

For API-only debugging:

```bash
cmake --build build --target user.docs.api
cmake --build build --target user.docs.api.versions
```

For normal local documentation development, use the same command as any ProperDocs project:

```bash
properdocs serve
```

The `properdocs-cpdoc` plugin runs cpdoc as needed and mounts its output into the live site. cpdoc's
working/output trees live below `../build/cpdoc/`, so semantic extraction never writes generated
reference files into the checkout.

Set `repo_url` in `properdocs.yml` to enable edit/source actions and issue links. The plugin derives
branch/tag-aware repository URLs for project Markdown pages.

## Installing documentation

The fully assembled documentation site participates in the normal CMake install after it has been
built:

```bash
cmake --build build --target user.docs
cmake --install build --prefix <prefix>
```

It is installed below `share/doc/<project>/`. Documentation is an optional install input, so an
ordinary library/binary install does not require `user.docs` to have been built first.
