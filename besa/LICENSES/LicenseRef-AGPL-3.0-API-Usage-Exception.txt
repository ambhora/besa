1. SPECIFICATION OF THE EXCEPTED API

The `excepted.api` distributed with a particular version of the Program
is the authoritative specification of the Excepted API for that version.
If no `excepted.api` is present, the Excepted API is empty and no
permission depending on the Excepted API is granted by this Exception.

`excepted.api` is a UTF-8 encoded plain-text file. Each line is either
blank, a comment, or exactly one path entry. A line whose first
non-whitespace character is `#` is a comment. Leading and trailing
whitespace is ignored.

Each path entry:

  a. is interpreted relative to the root of the Source Distribution;

  b. uses `/` as the path separator;

  c. must name exactly one regular file present in that Source
     Distribution;

  d. is matched case-sensitively against the path recorded in the Source
     Distribution;

  e. must not be absolute;

  f. must not contain `.` or `..` path components; and

  g. must not contain wildcard, glob, regular-expression, or directory
     matching syntax.

An invalid entry, including an entry that does not name a file present in
the applicable Source Distribution, designates no Interface. Invalid
entries do not enlarge the Excepted API.

The permissions granted for a particular version of the Program are
determined by the `excepted.api` distributed with that version. A later
version of the Program, a later `excepted.api`, or a later version of this
Exception does not retroactively narrow permissions already granted for
an earlier version.

NON-OPERATIVE IMPLEMENTATION NOTES

The following notes are not part of the Exception and grant no rights.

1. SPDX / REUSE

REUSE cannot at present represent a custom exception as an exception. The
combined terms are therefore represented by a project-specific
LicenseRef:

    SPDX-License-Identifier: LicenseRef-AGPL-3.0-API-Usage-Exception

with the combined terms provided as:

    LICENSES/LicenseRef-AGPL-3.0-API-Usage-Exception.txt

This is a compatibility representation, not the conceptual model. SPDX 3
defines AdditionRef as a first-class user-defined addition, under which
the terms are expressed as:

    AGPL-3.0-only WITH AdditionRef-AGPL-3.0-API-Usage-Exception

A tool that sees only the LicenseRef identifier cannot infer that the
base license is AGPLv3 or that the terms are copyleft. The readme,
package metadata, and licensing notice should therefore state in plain
words that the material is licensed under AGPL-3.0-only together with the
AGPL-3.0 API Usage Exception, version 1.0, even while source headers
carry the LicenseRef.

The project should distribute the text of AGPLv3.

This Exception applies only to AGPLv3. Projects using it should declare
AGPL-3.0-only rather than AGPL-3.0-or-later, so that a recipient electing
a later version of the License cannot leave the Exception behind.

2. Contribution policy

Inbound contribution terms must match outbound terms, stated outside the
license. A suitable policy is:

    Contributions are submitted under the same licensing terms that
    apply to the part of the project being modified. Contributions to
    material distributed under AGPLv3 together with the AGPL-3.0 API
    Usage Exception are submitted under those same terms.

    Every commit must carry a sign-off line:

        Signed-off-by: Jane Developer <jane@example.com>

    The sign-off certifies Developer Certificate of Origin 1.1.

The sign-off establishes the contributor's right to submit; the first
paragraph establishes the terms under which the submission is made. Both
are required for the Exception to remain enforceable across the whole of
the Program.

3. Validation of excepted.api

An invalid entry grants nothing as a matter of the license text. Project
tooling should nevertheless fail a build or release where:

  a. `excepted.api` contains a malformed entry;
  b. a listed path does not exist;
  c. a listed path names a directory rather than a regular file;
  d. an entry is duplicated; or
  e. a file intended to form part of the public Excepted API is missing
     from `excepted.api`.

Legal robustness means a typo cannot accidentally grant rights; developer
ergonomics means a typo fails immediately rather than silently narrowing
the boundary.

4. Scope of the boundary

The Independent Work definition is deliberately permissive. A work is not
disqualified by being small, by being a facade over the Excepted API, by
being commercial, or by being developed, built, and shipped alongside the
Program. The boundary is the contents of `excepted.api`. Narrowing it is
done by removing entries from that file, not by reading a purpose test
into this Exception.
